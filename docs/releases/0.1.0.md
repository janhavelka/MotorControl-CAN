# 0.1.0 software candidate

This is an unreleased development candidate, not a tag, package publication or
hardware-qualified product. `library.json` is the version authority and
`Version.h` is generated from it. The [prompt49 report](../reports/prompt_49.md)
records the package audit; the [independent final handoff](../reports/prompt_50.md)
records corrections, verification and inherited work. Use a commit as well as the version
when comparing development artifacts: the version alone does not identify an
intermediate checkout.

## Candidate scope

| Evidence layer | Available | Excluded claim |
| --- | --- | --- |
| Implemented portable C++11 | Exact units, quantization, logical axes/references, native values, Classical CAN and CANopen codecs; Lichuan typed reads/settings and conditional action/motion/commissioning/persistence lifecycles | No implicit I/O, clock, allocation, retry, drive enabling or motion |
| Host tested | Public request/event/result contracts, boundary failures, uncertainty, fixed-capacity ownership and source/installed consumers | Fakes and N5/EPOS4/proprietary contrasts do not install or qualify another profile |
| Firmware builds | Pinned S3 Arduino/IDF and S2 IDF paths; isolated core/component paths | Arduino S2 blocked; no complete P4 application or platform qualification |
| Physical observations | S2 with two user-labelled CL86-C drives and LC60H2127 motors, bounded communication and conditional motion trials | No complete motion, stop, electrical, sustained-failure or related-model qualification |

The [operation coverage](../reference/lichuan_operations.json),
[mechanical checker](../../scripts/check_lichuan_operations.py),
[feature coverage](../coverage.md) and [progress table](../prompts/PROGRESS.md)
separate descriptor, codec, read, setting, action/workflow, API, CLI and tests.
A metadata row or raw accessor does not fulfill a gated semantic operation.
API-only helpers have explicit rationale in the operation map. Lichuan always
builds in the single library; there is no profile-selection CMake option.

## Public descriptor migration

`LICHUAN_C::ObjectDescriptor` no longer contains `ownerPrompt`. Prompt ownership
is development metadata retained in `docs/reference/lichuan_objects.json`, not
a device fact or runtime API. Remove direct field access and the corresponding
positional argument from handwritten aggregate initializers. Prefer the named
constants in `Objects.h` where they match the intended object.

Rebuild the library and all consumers together. This is a source and structure
layout compatibility change even on a platform where padding leaves `sizeof`
unchanged. No stable binary ABI is promised for this development version.
Object addresses, widths, access decisions and firmware gates are unchanged.

## Dependencies and distribution decision

Core source packages contain the portable C++11 implementation, public headers,
CMake metadata, MIT license and selected user guides. Installed packages contain
headers, static library, relocatable CMake exports and license. Neither needs
Python, a sibling repository, SDK, ledger, PDF, EDS or CANopenNode. Descriptive
`Catalogue.h` is optional; numeric consumers do not require its strings.

Keep the pinned CANopenNode source at
`experiments/canopen_service_fit/vendor/CANopenNode`. Both the experiment and
optional application adapter use the same copy. The existing
[UPSTREAM manifest](../../experiments/canopen_service_fit/UPSTREAM.json),
CMake source-hash check and promptset integrity check already enforce its pin
`9b8beed8367241e96ac03f916cd5a500bcb2cf23`. Moving it would change paths without
improving the package boundary, so this audit deliberately retains it. The
adapter and owner remain optional repository targets, never installed core
dependencies. Preserve its Apache-2.0 license and original source notices.

Adapted MotorControl-RS code keeps its MIT attribution. ESP SDK/toolchain notices
stay with those dependencies. The GPL-3.0 public Lichuan example remains reference
material only; it is not compiled or exported. Vendor originals/full extracts,
copied snapshots, tests/tools and hardware logs stay excluded from core packages.
This audit authorizes no publication or new redistribution of vendor material.

## Inherited limits and next work

- Four standalone typed reads remain missing software scope: `605D` (prompt31),
  `2301/2302` (32) and `607A` (33). Existing action prerequisites/raw access do not
  substitute for them. This is a limited candidate, not whole-library completion.
- Prompt18/Q17: the narrow TPDO1 subset does not complete general remapping or
  qualify delayed samples on a reused route.
- [Device conflicts](../device_conflicts.md): status dialect, I/O layout,
  node/route activation, scale, velocity startup/reverse, release, homing and
  persistence gates remain feature-specific. No generic CiA402 fallback closes them.
- [Prompt47](../reports/prompt_47.md) and [prompt48](../reports/prompt_48.md) remain
  Partial. Controller reports do not replace shaft/standstill observations,
  independent CAN/electrical measurements, home/limit fixtures or related models.
  Prompt48's 64-byte serial diagnostic deficit remains unlocalized; a clean
  repeat does not resolve its cause.
- FieldCore integration is [prospective](../fieldcore_handoff.md). The current
  CANopen owner is not a ready proprietary-CAN backend; use the
  [new-drive playbook](../prompts/ADD_DRIVE.md) for additional products.

The [backlog](../backlog.md) retains exact owners and next measurements. Closing
this documentation/package audit changes none of those qualification states.
