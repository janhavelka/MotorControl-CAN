# S2 bench image internal memory: where it goes and how to save it (2026-11-12)

Question: why does the ESP32-S2 bench image run short of internal RAM when it runs
"a single task"? This report measures the linked image and the board's own `HEAP` replies, then
lists savings options with their measured or computed size, risk and contract impact.

Scope: investigation only. No firmware was flashed, no serial port was opened and no existing file
was changed. Every variant build went to `C:\t5`. Numbers are bytes unless stated.

## Short answer

The memory is not used by the task. The owner task's stack is 12288 bytes. The image keeps
about 210 KB of fixed, worst-case-sized application storage resident at the same time:

- two full `AxisSession`s (71504)
- the route with its 37592-byte record (42896)
- `FirmwareProbe` (31128): owner trace, typed acquisition history and the rest
- the shared record arena (23688)
- `SdoClient` (11056)
- `RouteWork` (8448)
- the console after `o` (15952) and 3856 per armed node

Many of these records never coexist, but each one has its own storage. The 320 KiB SRAM also
carries about 91 KB of SDK, ROM and cache use, which the IDF configuration can reduce by about
35 KB. Wi-Fi, Bluetooth, lwIP and mbedTLS are not linked (0 bytes each). The OPTAK S2 has no
PSRAM.

## Where the 320 KiB SRAM goes

The ESP32-S2 has 327680 bytes of internal SRAM (0x3FFB0000..0x3FFFFFFF on the data bus, aliased
as IRAM). IRAM and DRAM are one pool, so every byte of code placed in IRAM is a byte less heap.
There is also 8 KB of RTC fast memory, which the SDK adds as a low-priority heap region, and
8 KB of RTC slow memory, which is not heap.

| Area | Range | Bytes | Notes |
| --- | --- | ---: | --- |
| ICache 8 KB + DCache 8 KB | 3FFB0000-3FFB3FFF | 16384 | DCache serves only external RAM on S2, and there is none (see R1) |
| IRAM code (`.iram0.vectors` + `.text`) | 3FFB4000-3FFC16BB | 54972 | All SDK code: FreeRTOS 13132, HAL 8326, heap 7221, spi_flash 6915, hw_support 5997, ringbuf 4353, other 9028. No application code |
| `.data` | 3FFC16C0-3FFD2033 | 67956 | Application 60548, SDK 7408 |
| `.bss` | 3FFD2038-3FFD294F | 2328 | Application 267 |
| Heap r2 (after `.bss`) | 3FFD2950-3FFFBFFF | 169648 | The only region that can hold a route or a session |
| Heap r1 (startup-stack block) | 3FFFC000-3FFFFA0F | 14864 | Added after startup |
| ROM data | 3FFFFA10-3FFFFFFF | 1520 | Reserved |
| Alignment | | 8 | |
| **Total SRAM** | | **327680** | |
| Heap r0, RTC fast | 3FF9E000-3FF9FFE7 | 8168 | Used only when DRAM fails (`MALLOC_CAP_RTCRAM` high priority) |
| RTC slow | 50000000-50001FFF | 8192 | 32 bytes used, not heap |

The linker places statics only below `0x3FFDE000` (`dram0_0_seg`). The `esp_idf_size` report
shows 125256 used and 46776 remaining there. Memory above that address is used by the ROM
during boot and becomes heap afterwards, which is why large bench objects come from the heap.

**SDK and ROM share:** cache 16384, IRAM 54972, SDK `.data`/`.bss` 9469 (including the 1536-byte
ISR stack), ROM 1520, alignment 8 and SDK heap use about 8.9 KB. The SDK heap use is the region
use minus the reservations, at the first `M`: idle 1536, `Tmr Svc` 2048 and `esp_timer` 3584
stacks, three TCBs, the UART driver and TLSF control. In total the SDK, ROM and cache take
**about 91.2 KB**. The application is left with **244651** bytes: statics 60815, boot
reservations 146536 and 37300 free, including 7780 of RTC fast memory.

## Measured heap at runtime

From the board, same image (`HEAP` line, regions `start:size:free:largest`):

| Moment | free | largest | r0 RTC fast | r1 | r2 main |
| --- | ---: | ---: | --- | --- | --- |
| Boot, after the five reservations (`reserved=1f`) | 37300 | 20480 | 8168:7780 | 14864:4080 | 169648:25392 (largest 20880) |
| After `c` (TWAI node) and `o` (console) | 20644 | 7680 | 8168:7780 | 14864:840 | 169648:11968 (largest 7424) |

`minimum=32860` at the first reading is about 4.4 KB below `free`. This matches the main task's
3584-byte stack and its TCB, which existed while the reservations were made. After `app_main`
returned, they were freed, and that freed space is most of r1's 4080. After `o`, the largest block
is 7680, and it is in RTC fast memory. A soak (11008) can no longer be allocated, and each armed
node takes 3856 of what is left. Neither RTC block holds a route or a session.

The installed C++11 core (`libMotorControlCAN.a`) has **zero** static RAM. All of the storage
above is application, adapter or bench storage. The core's fixed context types are its
building blocks.

`DRAM_ATTR` places the zero-initialised owner statics in `.data` instead of `.bss`. That costs
60 KB of flash image and a boot-time copy, but no SRAM: the RAM would be the same in `.bss`.

The shared `probe_idf` OPTAK S2 image (p42 build) has the same profile: `.data` 76848,
`.bss` 2544 and a 160704-byte r2. Its console (`ProbeConsole` 6744, `ProbeDevice` 6664) is static
there.

## Savings options

### R1. IDF configuration (any S2 image; no code or contract change). Measured by linking.

Each variant was linked from the same sources. "r2 gain" is the change in the main heap region
(`0x3FFFC000 - _heap_start`) compared with the baseline's 169648.

| Variant (fragment added to `sdkconfig.defaults`) | IRAM | `.data`+`.bss` | r2 | r2 gain | Flash image |
| --- | ---: | ---: | ---: | ---: | ---: |
| b0 baseline (`-Og`, ICache 8 KB, DCache 8 KB) | 54972 | 70284 | 169648 | 0 | 712478 |
| b3 `CONFIG_COMPILER_OPTIMIZATION_SIZE=y` only | 48164 | 69912 | 176824 | **+7176** | 643894 |
| b1 `ESP32S2_DATA_CACHE_0KB`, `FREERTOS_PLACE_FUNCTIONS_INTO_FLASH`, `HEAP_PLACE_FUNCTION_INTO_FLASH`, `RINGBUF_PLACE_FUNCTIONS_INTO_FLASH` + `_ISR_`, `LIBC_LOCKS_PLACE_IN_IRAM=n` | 32948 | 69364 | 200776 | **+31128** | 712766 |
| b2 = b1 + `-Os` | 29512 | 69072 | 204512 | **+34864** | 644046 |

b1 attributed (per archive): DCache 8192 (IRAM origin 0x40024000 -> 0x40022000), FreeRTOS
-9682, heap -7221, ringbuf -4101, newlib locks -744, esp_mm -114 and HAL `.data` -920.

Risk:

- **DCache 0 KB: low.** On S2, flash rodata (DROM0) is fetched through the ICache. The bootloader
  unmasks `EXTMEM_PRO_ICACHE_MASK_DROM0`, and IDF permits 0 KB only without SPIRAM. Not yet booted.
- **FreeRTOS, heap, ringbuf and locks in flash: low to moderate.** These functions cannot run while
  the flash cache is disabled. Nothing here runs then: there is no IRAM ISR (`TWAI_ISR_IN_IRAM`,
  `UART_ISR_IN_IRAM` and `GPIO_CTRL_FUNC_IN_IRAM` are off) and no runtime flash write (no NVS, OTA
  or `esp_flash_write` linked). The possible cost is ICache-miss latency in the owner loop. It needs
  one bench boot and the short regression with the existing service-gap figures.
- **`-Os`: low.** The p42 stack gate already covers S2 `-Os` (frame 2048 / chain 6144). It changes
  code timing.
- **`scripts/check_firmware.py`:** its pinned `BENCH_SDKCONFIG` keys do not include these
  options. Review whether the new values should be pinned.

Also computed, not linked: `CONFIG_ESP_TIMER_TASK_STACK_SIZE` 3584 -> 2048 gains 1536 heap. No
`esp_timer_create` symbol is linked, so the task has no callbacks. Low risk.

Checked and not available on S2:

- `CONFIG_FREERTOS_USE_TIMERS=n` fails to link: `esp_twai_onchip.c` calls
  `xTimerPendFunctionCallFromISR`.
- `SPI_FLASH_PLACE_FUNCTIONS_IN_IRAM`, `ESP_SYSTEM_IN_IRAM`, `LOG_IN_IRAM`, `ESP_TIMER_IN_IRAM`,
  `ESP_INTR_IN_IRAM` and `LIBC_MISC_IN_IRAM` are adjustable only with `SPI_FLASH_AUTO_SUSPEND`,
  which S2 lacks.
- `SPI_FLASH_ROM_IMPL` needs `ESP_ROM_HAS_SPI_FLASH`, which S2 lacks.
- `ESP_HW_SUPPORT_FUNC_IN_IRAM` forces the RTC/periph/regi2c IRAM options.
- ICache is already at its 8 KB minimum.
- Memory protection costs no alignment gap here (`_iram_end` 0x400316BC, `.data` at 0x3FFC16C0).

### R2. One record arena for everything that never coexists (bench only, `examples/s2_bench`)

`main.cpp` already makes these records mutually exclusive. Its rule is "A trial record, active or
retained, admits nothing else but inspection and release". A route starts only with
`!record && !rawRecord && !pdoRecord && !trialHeld && !commissionHeld`. A soak and a capture need
the same and also refuse during each other. The raw history is "never concurrent with typed
acquisition" ([firmware_examples.md](../firmware_examples.md)). The `PdoWatch` runs beside any
record and stays separate.

| Moved into the arena | Today | Bytes |
| --- | --- | ---: |
| `RouteRecord` (out of `BenchRoute`) | reserved | 37592 |
| `DeviceEvidence` (out of `FirmwareProbe`) | static | 14288 |
| Existing occupants | reserved | 23688 |
| Raw/PDO plans and review statics | static | 4144 |
| `Soak`, `SilentCapture` | lazy | 11008 + 7608 |

The arena would then be 37592 bytes, the route record. The always-resident saving is
79712 -> 37592 = **-42120**, and **-60736** in a boot that also uses the soak and the capture.

Risk is moderate: the change is lifetime bookkeeping. Each kind keeps its own increasing
identities, as the arena already does. The `DeviceEvidence` part changes `examples/common`
(`FirmwareProbe` takes borrowed record storage) for the shared images too. Before moving it,
verify the console's own acquisition record lifetime against `consoleHeld`. There is no core
contract change.

### R3. One operation slot in `AxisSession` (`examples/common`, not the installed core)

`busy()` includes `enableActive`, `moveActive`, `velocityActive`, `homeActive` and `clearActive`.
Every `request*` checks it first (`AxisSession.cpp` lines 72, 192, 203, 268, 420, 646, 855 and 1098).
So at most one of `enable_`, `move_`, `velocity_`, `home_` and `clear_` is active at a time.
Persistent facts are separate booleans: `moveFenced_`, `velocityNeedsStop_`, `homeNeedsStop_`,
`clearBlocked_` and `faultBlocked_`.

One slot for these five operations (largest 5152) instead of 19840 saves **-14688 per session**
(35752 -> 21064), so **-29376** on the bench. `stops_[2]` stays separate, because a QUICK_STOP
escalation reads the running HALT.

Risk is moderate and the change is visible to example callers: `enableAction()`, `moveAction()` and
the other accessors keep only the latest operation's context. Review the references made after an
operation ends: a counter clear's deferred owner synchronization, and an enable's read used as
stop state. The existing host tests exercise these. There is no core change.

### R4. Owner and SDO adapters (`adapters/owner`, `adapters/canopennode`; built in-tree, not installed)

- **Owner trace.** Each `Diagnostic` (384) embeds a 264-byte `Completion` that only `TERMINAL`
  entries use. Moving 24 frame entries of 120 bytes and an 8-entry terminal ring out of the trace
  is about **-4200**. Making `TRACE_CAPACITY` an application choice is the alternative. This
  changes the adapter's diagnostic API.
- **PDO routes.** `SdoClient::PDO_ROUTES = 8` costs 856 each (6848). An application without TPDO
  could compile fewer. The capacity is a compile-time constant today.

### R5. Installed core contracts (C++11, caller-owned fixed types): review, do not rush

- `ReadProvenance` copies the full 32-byte `Binding` per field, although the context keeps a
  frozen target. That is 150 copies, or 4800 bytes, per `AxisSession`; 3840 remain after R3.
- `SdoCompletion` keeps both the transfer's 32-byte download buffer and a 32-byte upload buffer,
  and only one is meaningful per direction. That is 1792 bytes per `AxisSession` (56 completions)
  and 1568 in `FirmwareProbe`.

Both change public evidence contracts and need the ledger and contract review. Their value is
smaller than R1 to R3.

### R6. RTC memory and PSRAM

- **RTC slow memory: 8160 bytes unused.** It is not heap. It could hold cold static buffers
  through `RTC_DATA_ATTR`, for example the bench plans (4144). It sits on a slower bus, keeps its
  contents across resets (the bench must clear it at boot, so that a stale record is never
  read as new evidence), and its access widths should be confirmed on S2 first.
- **RTC fast memory: 7780 free.** It is already counted in `free`, but used only when DRAM fails.
  Allocating one console block of about 6.7 KB there on purpose with `MALLOC_CAP_RTCRAM` keeps
  r2's largest block larger. This improves layout, not capacity.
- **PSRAM:** the board has none (ESP32-S2FH4, -N4 module), and the core must not need it anyway.

## Multi-drive: memory per concurrently moving axis

Each concurrently moving axis needs its own `AxisSession`, plus `ProbeMotion` when the console
drives it. `CanBusOwner::SEQUENCES = 2`, `URGENT_REQUESTS = SdoClient::CHANNELS = 2` and
`PDO_ROUTES = 8` fix the stack to two axes per interface today, whatever the memory. Raising them
costs per axis: one SDO channel 1520, one urgent owner slot 432, a reservation 80 and a health
record 112, which is 2144. Four TPDO routes add 3424. The six shared ordinary owner slots
(432 each) may also need raising for more than two axes in motion.

| Per axis | Today | After R3 |
| --- | ---: | ---: |
| `AxisSession` | 35752 | 21064 |
| `ProbeMotion` | 3528 | 3528 |
| Adapter capacity | 2144 | 2144 |
| **Per axis, no PDO / with 4 TPDO** | **41424 / 44848** | **26736 / 30160** |

The fixed part of a lean multi-axis application, without bench records and `DeviceEvidence`, is
about 47080 bytes:

| Item | Bytes |
| --- | ---: |
| Owner, without its per-axis parts | 12216 |
| `SdoClient` base | 1168 |
| TWAI driver and adapter | 1440 |
| Platform and `ProbeApp` | 2980 |
| Owner stack and TCB | 12624 |
| Console | 15952 |
| TWAI node allocation, estimated | about 700 |

The application budget is the 244651 bytes measured above, 279515 with R1 (b2), or 281051 with
the `esp_timer` stack too.

| Configuration | Axes that fit, no PDO | With 4 TPDO each |
| --- | --- | --- |
| Bench image today | 2 (no block of 35752 is left) | 2 |
| Lean application, today's SDK config | 4 ((244651-47080)/41424 = 4.8) | 4 |
| Lean application + R1 | 5 (5.6) | 5 |
| Lean application + R1 + R3 | 8 (8.7) | 7 |
| Bench image + R1 + R2 + R3 | About 119 KB free after console and two armed nodes, room for four more 27064-byte axes. The bench routes still address only nodes 1 and 2 | |

These are capacity counts, not a contiguity guarantee. Sessions must still be reserved first, in
the largest region, as `BenchHeap.h` does: r2 is 204512 bytes with R1 and is the only region that
holds a session. The counts are not timing, bus-load or service-gap qualification either. Several
axes in motion multiply owner traffic, which needs its own measurement.

## Recommendations, in order

1. **R1, now.** Add the b1 fragment and `-Os` (b2) to the S2 images, plus the `esp_timer` stack.
   This gives **+34864** heap (+36400 with the stack) with no code change. Next measurement:
   one bench boot, an `M` reading, and the short route/console regression with the
   service-gap figures.
2. **R2 on the bench.** Unify the route, acquisition, raw/PDO/D/K/H, soak and capture records into
   one 37592-byte arena: **-42120** always resident, **-60736** when the soak and capture run.
3. **R3 in `AxisSession`.** One operation slot: **-14688 per axis**. This is the change that makes
   multi-axis applications fit (8 axes with R1 instead of 4).
4. **R4 later**, if an application needs it: owner trace (about -4200), PDO routes (856 each).
   R5 only with a contract review.
5. **Not worth doing:** removing Wi-Fi, BT or TLS (none is linked), disabling FreeRTOS timers (the
   TWAI driver needs them), PSRAM (none on the board), or shrinking the 12288-byte owner stack
   (5944 used, against a lower-bound chain of 5888).

## Limits of this report

- The variant images were linked, not booted. R1's runtime effect (DCache 0, functions in flash)
  and the exact SDK heap use are not measured on hardware.
- The SDK heap use (about 8.9 KB) and the TWAI node size (about 0.7 KB) are differences of
  measured totals, not per-allocation traces.
- R2 to R5 savings are computed from DWARF `sizeof`. Real heap blocks add a few bytes of header
  and alignment each.
- The numbers in the `s2_bench` README are from an older build: `BenchRoute` 42624, `RouteWork` 8432
  and `AxisSession` 35592 there; 42896, 8448 and 35752 at `e693f16`. The README was not changed.
