### Concrete evidence to recheck

Use [motion facts](../audit/LICHUAN_MOTION_FACTS.md) for user-facing units and capability reasons: ramp times are ms; position-profile speed and velocity-mode target are different objects; homing methods require different signals; setting/clearing a host origin is different from `2302` device clear. A motion command must not silently select an unresolved status dialect, reverse-velocity encoding or enable sequence. Rates are rpm objects: never write `effectiveNative` to an rpm object unless the prepared `rateBasis` is `MOTOR_TURNS`, its `rateTime` is `MINUTE` and its representation is integer. `nativeVelocityTime` defaults to `SECOND` and the basis to `COMMAND_INCREMENTS`, and both give in-range wrong values: 1 load turn/min at 3,200 increments per turn and gear 5 gives 267. A negative test must pin that such a target is refused before any write; quantize once and report error in rpm. Define `native` for CAN velocity in the grammar as the configured [native-rate dimension](../axis_contract.md#signed-velocity-and-the-native-rate-destination): RS's `velocity 60 rpm native` works only on an `AxisConfig` with `MOTOR_TURNS` and `MINUTE`, and rejects on any other. RS `moveby VALUE [unit]` carries no speed or ramp argument and CAN forbids the boot defaults it relies on, so simple-move intent (`moveby`, `moveto`, `speed`, `accel`, `decel`, `motion`, `stepsperturn`) is host intent in this prompt: an unset speed, ramp or scale rejects before admission, and `moveto` needs an explicit `axis origin`. The public example's hidden save during zeroing is a specific negative CLI/runner regression.

## Implement

1. Add the accepted `moveby`, `moveto`, `move relative`, `move absolute`, `move angle`, `velocity` and `home` routes using the same typed requests/native preparation as direct C++ callers. Preserve exact units, angle policy, coordinate/reference meaning, duration/deadline and preparation timing. CLI conversion code must not become the only implementation of a motor feature.
2. Add supported `enable`, `motor-release`, `alarm-clear`, `position-clear`, `stop normal` and `stop fast` actions through public operation APIs. Preserve profile-specific action/stop semantics and unresolved firmware gates. Distinguish device release from `release ID`, and physical stop from local `cancel` or host `recover` in help and result records.
3. Complete application dispatch for admitted operation IDs, terminal results, explicit release and urgent stop capacity. Preserve the original failed/uncertain motion result when a later stop succeeds or fails. Stop follows the contract W6 is to deliver (DEC-2, DEC-8; project decisions, not vendor evidence): a stop never cancels in-flight work and waits for it to settle; after an unconfirmed motion write, an explicit best-effort `000B` may be transmitted once on the unresolved route and its reply never qualifies; a stop with no accepted byte is held across one bounded recovery and sent once, and a second fault ends it not transmitted; a lost reply stays UNKNOWN and is never resent; `stop fast` escalates a running `stop normal`, never the reverse (RS has no such policy check on supersede; this difference is deliberate). `cancel` of sequenced work or a typed read, and `monitor off`, let in-flight frames settle. Application dispatch holds one operation and one reservation today (`ProbeApp` `read_`/`pending_`); concurrent operation, stop and result handling need one concrete per-axis session, not a framework. Until those contracts are implemented, stop routes stay gated and this prompt reports them so. No timeout, console disconnect or selection change automatically retries a movement or re-enables a drive.
4. Finish command/API/help/capability coverage across prompts 40–42. Publish one canonical inventory with actual grammar, capability, API, mutation class and completion shape. Native settings/network commands apply only to matching profiles. No removed RS alias should reappear inadvertently, and no survey-only profile may appear as supported.
5. Rebuild both firmware examples using the actual shared console, application and owner. Verify matching command inventory, routes, payload units, schema and behavior on native/Arduino/IDF. Platform startup, USB and clock differences remain thin adapters; there is no private firmware-specific motion path. The S2 bench board is the physical fixture and is not covered by the S3 console firmware; record whether the shared console runs on S2 (UART console, single core) or remains a named backlog assignment, without a Markdown link to prompt 27 or 28.
6. Complete bounded console/load behavior. Passive debug copies ordinary traffic. Reserve owner service and stop admission under full output queues, long invalid input and bursty events. Record dropped output explicitly, preserve complete JSONL records and never consume a frame away from normal dispatch to capture it.
