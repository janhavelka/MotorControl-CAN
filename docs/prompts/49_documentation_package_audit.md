## Objective and boundaries

Audit usable documentation, package/export boundaries and support coverage as a new user and maintainer. Close confirmed omissions in existing contracts rather than writing source documentation for the first time. Produce a coherent software candidate with physical limitations explicit. Final independent hard-contract review and exact-commit verification follow in prompt 50. This prompt does not authorize release tags, package publication or republishing vendor material.

## Read and audit

Refresh RS source/install/package/version and documentation conventions plus ADS1115/INA228 checker/Doxygen/release practice. Inspect actual target code, exported headers, consumers, workflow commands, generated ledger, CLI, runners and retained reports. Review current FieldCore only to verify the handoff's prospective claims. Apply the complete inventory in [DOCUMENTATION.md](DOCUMENTATION.md), [CONVENTIONS.md](CONVENTIONS.md), [MULTIDRIVE.md](MULTIDRIVE.md), [MAINTAINABILITY.md](MAINTAINABILITY.md) and [DELEGATION.md](DELEGATION.md).

## Implement

1. Follow README alone through native install/include/link and an ordinary exact preparation/read/move/stop example using public functions and supplied events. Then verify separate firmware build/configuration and Python offline/live instructions. Every documented command must exist and match its actual prerequisite, traffic and evidence behavior; hardware configuration is not a requirement for pure native use.
2. Audit general files: README/docs index/source map, CHANGELOG, CONTRIBUTING, SECURITY, LICENSE, AGENTS, metadata, Doxyfile and formatting guidance. Keep verified reporting routes/version policy honest; do not invent addresses or guarantees. Describe public semantics/migration in CHANGELOG rather than agent activity.
3. Audit maintained contracts for units/axis/reference, profile/native coverage, service/owner/health, CLI/JSONL, verification, commissioning, bench/scenarios and prospective consumer integration. Check public declaration/field/enum documentation, implementation invariants and Python helper docstrings. Prefer one authoritative contract linked from reports instead of duplicated contradictory prose.
4. Finalize descriptor/codec/read/setting/action/workflow/API/CLI/test coverage independently. Every confirmed in-scope feature has real typed code, tests and CLI coverage or an explicit API-only rationale. Missing confirmed work remains unfinished. Keep researched, fixture-tested, implemented, firmware-built and physically qualified inventories separate; unresolved documentary facts withhold the affected support claim.
5. Verify one version source and generated freshness across manifests, headers and documents. Check source/install/export consumers, selected-profile options, PlatformIO, IDF component and standalone Arduino/IDF examples. Core packages require no sibling, Python, PDF, SDK or stack unless an adapter is explicitly selected.
6. Audit distribution/license boundaries. Preserve MIT attribution for adapted code and actual stack/SDK license notices. Exclude vendor PDFs/EDS/full extracts, copied snapshots, tests/tools and hardware logs from distributable core software. Local acquisition does not establish redistribution rights; verify those separately before any future publishing. Preserve original reference bytes and provenance in this repository.

## Verify and exit

Run strict Doxygen and confirm real public free functions/generated declarations appear in outputs. Check maintained links and actual example compilation, not only warning-free empty extraction. Run package consumers and freshness checks affected by fixes. Reconcile support text with retained hardware status; never claim all CAN motors or universal CiA402 compatibility. Review the new-drive playbook and document bounded architecture extension limits without listing design fixtures as supported products. Do not mark pending qualification complete or archive its obligations.

## Documentation and delegation

Update existing user docs/release-candidate notes and source map; remove obsolete duplicate instructions only after fixing inbound references and preserving history. Normal engineering agents can independently follow native/firmware instructions or inspect package contents on disjoint paths. Use stronger review for support/units/evidence claims. The lead owns support wording and reconciles findings, following [DELEGATION.md](DELEGATION.md) for models and same-branch work.

Close this prompt's owned scope and checks; record `docs/reports/prompt_49.md` with verified user workflows and remaining evidence limits. Commit and sync on the same recorded execution branch before handoff, including useful complete checkpoints when appropriate.
